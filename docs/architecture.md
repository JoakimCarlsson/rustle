# Architecture

Rustle is split into layers. Each crate depends only on the ones below it, and a renderer depends on nothing above `rustle-graphics`.

## Frame flow

1. `rustle::run` creates a `Composition` through `rustle_ui::composition(root)`.
2. A pass runs the root composable. `text`, `column` and the other composables push `Node`s into the current scope. Every composable call site opens a group, and `remember` reads or creates state in its group. The pass returns a `Node` tree. Effects the pass scheduled run when it has finished.
3. `rustle_ui::display_list` measures the tree within the window's constraints. Each node applies its modifiers from the outermost in, then its `Layout` policy measures the children. Text is measured by the renderer through `TextMeasurer`. The measured tree is then painted into `DrawCommand`s plus the clickable, pressable, draggable, scrollable, focusable and described regions.
4. `rustle_wgpu::Renderer::render` draws the commands in order. Consecutive rectangles are drawn together, then the text or pictures that follow, so later commands paint over earlier ones, each cut to the clip in effect. Commands that lie wholly outside the clip are dropped first, so a long column inside a scrolling area costs what is visible.
5. Animations and suspending tasks ask the runtime's frame clock for the next frame. The first request wakes the event loop, which then redraws each frame, runs the requested callbacks (they change state and wake tasks), composes and lays out again, and draws. When nothing is left to run, no more frames are requested.
6. Input is hit-tested against the regions of the latest layout. Areas are told apart by where they are and how big, never by their handlers, because every recomposition makes new handlers (and an animation recomposes every frame), so a press is matched to its release by area and the handler that runs is the current one. A press and a release on the same clickable runs its handler; a press focuses the focusable under it and runs press and drag handlers, and a drag keeps going while the button is down; the wheel scrolls the innermost scrolling area under the pointer.

   Pointer buttons: the primary button (or a touch) drives clickables, focus, drags and long presses as before. Every button, the primary one included, can also be listened to with `Modifier::on_pointer_button(button, ..)` and its shorthands (`on_secondary_click`, `on_context_menu`, `on_middle_click`, `on_back_click`, `on_forward_click`, `on_primary_click`, `on_button_drag`). Those areas are hit-tested per button: the topmost area that listens to the button gets it, and a region for one button never blocks the others, so a parent's `on_context_menu` works over a child's `clickable`. Each `PointerEvent` says which button, the phase (`Press`, `Drag` while held, `Release`, `Click` when released on the area it went down on), the position in the area and in the window, the modifiers held, and the click count.

   Keys: a key event (`KeyEvent`) carries the logical `Key` (with `F(n)`, `Insert`, `PrintScreen`, `ContextMenu`, lock and modifier keys), the `PhysicalKey` (a `KeyCode` named like the W3C `code`, independent of layout), the `KeyLocation`, `repeat`, and `pressed` (false for a release). It is given, stopping at the first handler that returns true, to: the `on_preview_key_event` areas around the focused area (outermost first), the focused area's `focusable` handler, then the `on_key_event` areas around it (innermost first). With nothing focused every key area in the window is around it, so a root `on_key_event` holds the application's shortcuts. Only when none handled it do Tab and Escape move or drop focus. `KeyEvent::is` matches a logical key plus exact modifiers and `KeyEvent::is_code` a physical one.

   Input methods: winit's `Ime::Preedit` is stored on the focused `Focus` (`Focus::preedit`). Text fields insert the composition at the caret, underline it, and keep it out of their value until `Ime::Commit` arrives as typed text. While a field is being edited, layout reports its caret rectangle in `DisplayList::ime_area`, and the window passes it to `set_ime_cursor_area` when it moves, so the candidate popup follows the caret. The window allows IME input while something has focus.
7. `State::set` and `State::update` only mark the composition dirty. The first clean-to-dirty change sends a winit user event. If the state was read inside `restartable` blocks only, the event loop composes just those blocks again, in place; if the root read it, or nothing composing is known to have, it composes the whole root again. Either way it then lays out again (steps 3 and 4), where the layout of every `restartable` block that did not change is reused. Several updates before that event cost one pass. Resizing the window or changing its scale also lays out again, without composing.
8. `RUSTLE_SNAPSHOT=out.png` (or `rustle::preview`) runs steps 2 to 4 once against an offscreen renderer and writes the frame as a PNG, which is how the layout of a composable can be checked without a window. `RUSTLE_SNAPSHOT_INPUT` replays input first, as `;`-separated steps: `click:x,y`, `rclick:x,y`, `mclick:x,y`, `backclick:x,y`, `forwardclick:x,y`, `move:x,y`, `type:text`, `key:Name` (logical, such as `F5`, `Escape`, `a`), `code:KeyA` (physical), `release:Name`, `mod:ctrl+shift` (modifiers held for the steps after; `mod:none` clears), `preedit:text` and `commit:text` (an input method composing and committing in the focused field), and `drag:x1,y1,x2,y2` (a mouse drag as the gesture modifiers see it).
9. After each layout the described regions are sent to the platform's accessibility API as a tree (a description made inside another is its child, siblings are ordered by traversal index), and its requests to click or focus are run.

## Identity and state

Every `#[composable]` function, layout (`column`, `row`, `stack`, `button`, ...) and `remember` call opens a group identified by its source location, using `#[track_caller]`. State belongs to its group, so:

- a call inside an untaken `if` leaves the composition, drops its state and runs its cleanups, without disturbing its siblings;
- calls from the same site, such as in a loop, are matched by order. Wrap each item in `key(id, || ...)` if items can be inserted, removed or reordered;
- groups the root did not reach in a pass are dropped after it, outside any borrow.

Effects run after the pass: `side_effect` every pass, `disposable_effect` when its key changes, with a cleanup before the next run and when it leaves the composition, and `launched_effect` starts a task that waits on frames and time, cancelled when its key changes or it leaves. `CompositionLocal` passes values down the tree, and an inner `provide` overrides an outer one.

## Skipping

`#[composable(skippable)]` and `skippable(deps, || ...)` skip their body when called again with equal `deps` and when none of the state or composition locals read during the last run has changed. State reads are recorded with the version they had; locals are recorded as a check that the value is still equal. A skipped block keeps what it remembered and re-emits the nodes it produced. Effects inside it do not run again.

## Scoped recomposition and the layout cache

`restartable(deps, content)` runs `content` in a group that remembers what it read and stands in the tree as one node (`Content::Scope`). State records which scopes read it, and the root separately. A write invalidates the scopes that read the value; only when the root read it, or no scope is known to have, is the whole root invalidated. `Composition::recompose` then runs each dirty scope in place (finding its group, running it with the composition locals it saw, and putting the group back) and keeps everything around it, so the root and the siblings do not run. A scope called again by running code is skipped when its `deps` are equal and nothing it read changed, like `skippable`. Reads in a `Subcomposition` count as the root's, so lazy content keeps recomposing as before.

Layout reuses work per scope. Measuring a `Content::Scope` records, through `track_reads`, the state read while measuring (a scroll offset, a `Modifier::layout` closure that reads state), the scopes inside, the constraints, the text measurer and `rustle_text::font_epoch`. The measured subtree is kept in the scope's `user_data` as a `Paint::Shared` and reused while all of those are as they were. Subtrees that compose content while measuring (`Subcomposition`) or lay out editable text are never cached, because their effects cannot be replayed. Painting still walks the cached subtree every frame, so only measuring is saved; there is no cache of draw commands or regions.

`remember` is snapshot-aware: its state reads as a `Snapshot` saw it and keeps writes made inside a `MutableSnapshot` until it is applied. It needs `T: Clone`; `remember_live` is for values that cannot be cloned and are always live.

Measured with `cargo run --release --example bench` (600 rows, about 2400 draw commands, 900×700, 300 frames, one changing bar; medians, release build):

| Mode | Compose | Layout + paint | Render + readback | Total median | p95 | p99 |
| --- | --- | --- | --- | --- | --- | --- |
| plain (root recomposes) | 0.99 ms | 0.88 ms | 2.36 ms | 4.22 ms | 7.45 ms | 9.04 ms |
| skippable rows | 0.48 ms | 1.03 ms | 2.29 ms | 3.82 ms | 7.40 ms | 9.20 ms |
| restartable bar and list | 0.01 ms | 0.24 ms | 2.37 ms | 2.68 ms | 4.65 ms | 5.36 ms |

The `effects` scenario (`BENCH_SCENARIO=effects`) draws a grid of 300 cards straight to the renderer at 1920×1080, each a rounded clip holding an alpha effect layer and, for every third card, a backdrop blur (about 1600 commands; render and readback, medians over 60 frames, release build, one GPU, offscreen):

## Where new things go

- A composable that only arranges or draws children, such as `row`, `box` or a lazy list: `rustle-foundation`.
- Something every composable can take, such as `Modifier`, constraints and measurement: `rustle-ui`, because modifiers and layout depend on each other.
- A unit, size constraint or geometry type: `rustle-unit` or `rustle-geometry`.
- Anything about how text looks or is measured: `rustle-text`. The renderer implements the measuring interface that layout calls.
- A new kind of drawing instruction: `rustle-graphics`, then support in each renderer.
- A new layout, such as a grid: implement `Layout` in `rustle-foundation`.
- Animated values, easing, springs and transitions: `rustle-animation`, built on the runtime's frame clock and tasks.
- A component with a look, such as `button`, or theme values: `rustle-widgets`.
- Screens and moving between them: `rustle-navigation`.
- A new renderer backend (Skia, Vello): its own crate depending on `rustle-graphics`.
- Platform integration for another OS or toolkit: alongside `rustle`, not in the layers above.

## Embedding

`App`, which serves native windows, and `Embedded`, which serves an area a host gives it, share one window-free core, `Interface` (`crates/rustle/src/interface.rs`): the display list and the pointer, hover, drag, carrying, focus and key state, with the handling of every input that changes them (`pointer.rs` and `focus.rs`). Nothing in it touches a window. What a window would be asked to do (draw again, show a cursor, allow an input method) is recorded in it, and `App` applies that to its window after each event (`App::apply_effects`) while `Embedded` returns it to the host (`update` says whether to draw, `cursor`, `has_focus` and `ime_area` answer the rest). `App` keeps one `Interface` per window and swaps them as it did the fields before (`Interface::exchange`, which leaves the modifier keys, buttons held and reported caret area shared).

An `Embedded` is given its size and scale with `resize`, and the host calls `update` once per frame. Its input methods answer whether the interface used the event, from `DisplayList::interactive_at`: something that reacts to the pointer is there, or an area marked `Modifier::blocks_pointer`, which makes its whole rectangle count, so the empty space of a panel is not given to what lies beneath. The wheel answers true when a scrolling area took it or the pointer is over a blocking area. Blocking only changes what the host is told; areas under a blocking one still get their events inside the interface.

Input methods: `preedit` stores the composition on the focused `Focus`, as the window's `Ime::Preedit` does, `commit` types the final text, and `ime_area` is the caret rectangle in the area's logical pixels, `None` while no field is edited, for the host to give its input method as the candidate popup's place. `has_focus` says whether the host should send the keyboard and enable the input method.

`set_root` replaces the root composable and keeps the renderer, with its fonts and caches, and the size, scale and appearance. The composition is made anew, because state remembered by an old root cannot be matched to a new one (a reloaded library has different call sites and types), so the old one is dropped, which runs its effects' cleanups, and the interface state that points into it (focus, hover, drags, the display list) is cleared. A host that unloads the code of the old root calls `set_root` before unloading.

`viewport(width, height, on_rect)` reserves an area that draws nothing and calls `on_rect` with its rectangle in logical pixels from the top-left of the embedded area, after layout, when the rectangle changed. The host draws there before or after the interface, with the interface drawn over its own frame (`render_into` with no clear). `on_rect` may set a `State`: it is not called again for an unchanged rectangle, so layout settles.

Saved values: `set_saver` installs the `Saver` that `remember_saveable` reads and writes, which is how a host keeps them in its own storage. It applies to the whole thread.

Several `Embedded` can live on one thread, each with a renderer of its own. The text functions of `rustle-text` reach one engine per thread, so the renderers share one font system and one engine, installed by the first: a font registered with `register_font` reaches all of them, and the installed fonts are loaded once. Before this each new renderer replaced the engine, and a font registered afterwards reached only the last one made. Other thread-wide state is shared by all: the saver, the clipboard and the focus request, which an `Embedded` consumes at the end of every call that can run application code, so it cannot be taken by another. `window` composes inside an `Embedded` but opens nothing.

## Windows

The root composable is shown in the main window. `window(options, on_close_request, content)` composes `content` inside the same pass, so it shares state, composition locals and the theme with its parent, but the resulting tree is not emitted into the parent: it is stored in a per-thread registry under a key remembered in the call's group, and a `disposable_effect` removes the entry when the call leaves the composition. The event loop looks at the registry when it idles (`about_to_wait`, and after each window event): new entries get a native window, renderer and accessibility adapter, removed ones are dropped, changed titles and other live options are applied. Events are routed by `WindowId` (`Host::window_event` takes it). The input code is written against one window's fields on `App`, so the fields of the window being served are swapped in from `App::slots` when its event arrives (`crate::windows`); after composing, every window is laid out again from its own tree. `WindowHandle::drag_window` and `drag_resize_window` hand the pointer to the system, which never sends the release, so the press state of that window is cleared afterwards.

## Current limitations

- Custom shaders, layer effects and backdrop blur: a `ShaderBrush` sees `uv`, the position, time, size and up to 16 floats, with no textures or other bindings, and a layer effect, rounded clip or layer draws through a texture sized to what it holds (the clip, or the whole window when nothing clips it). A blurred effect is cut to its rectangle and its edges are clamped, not faded. Backdrop blur reads the frame drawn so far, including what lies below the group it is in, and makes the frame render through an extra texture, so a host that draws over its own frame (`render_into` without a clear) has its own pixels blurred only if they are in the texture; a blur there sees the interface alone; the multiply, screen, darken and lighten blend modes treat what is below as opaque. Effects do not change where pointer input goes.
- Intrinsic sizes come from the layout policies' own answers (`Layout::min_intrinsic_width` and the three others), the text measurer, and the modifiers in front of the content. A `Modifier::layout` is looked through, not asked, and `lazy` lists and scrolling areas answer like any other layout. `Subcomposition` content composed while measuring has its own state, but that state is cleaned up when a slot is not composed in a measurement, and composition locals are those of the last pass that called the owning composable. `constraint_layout` solves each axis independently, does not mirror in right-to-left layouts, and a child with fewer than two anchors on an axis cannot fill it.

- Windows are only opened and closed from the event loop, so a window appears after the pass that asked for it, not inside it. A secondary window never closes itself: its `on_close_request` must stop the `window` call. The main window cannot be opened or closed from composition. Window transparency, per-window themes, window positions, fullscreen, modal and parent/child relationships are not supported, and `preview` draws only the root. Keyboard focus is tracked per window, but a window that loses OS focus keeps showing its focused control as focused.
- State is single-threaded (`Rc`), and `State` handles are not `Copy`, so closures need clones. Tasks wait on frames and time, not on other threads.
- State read by the root (or by nothing that composes) still recomposes the whole root; only state read inside `restartable` blocks recomposes just those blocks. A `restartable` block is one node (several are stacked in an `Overlay`), takes its inputs as `deps` and a `'static` closure, and a state once read by the root stays a root read. Layout is cached per scope and painting is not: the cached subtree is walked and painted every frame, and subtrees that subcompose or edit text are never cached. Text sizes are cached and offscreen drawing commands are skipped by the renderer, but ordinary scrolling columns still compose and measure all their rows. `cargo run --release --example bench` measures a non-lazy list (600 rows, roughly 3000 nodes by default) with one changing value in plain, skippable and restartable modes (numbers above); `BENCH_ROWS` and `BENCH_FRAMES` control its size and positive measured-frame count. It reports stage medians and total-frame median/p95/p99; rendering includes offscreen synchronization and readback, not native presentation or isolated GPU time. Blocks marked `skippable` (or `#[composable(skippable)]`) skip their body when their arguments are equal and nothing they read has changed, but their parent still runs and their output is still laid out and painted. Snapshot state covers `remember` and `mutable_state_of` (`remember_live` values are live), and `derived_state_of` recalculates when what it read changed.
- `lazy_column`, `lazy_row` and `lazy_vertical_grid` need items of one fixed size and have no content padding or spacing (use `lazy_list_with` and its `LazyContent` for those); `lazy_list` and `lazy_horizontal_list` take any heights or widths but estimate the ones they have not laid out yet, so the scrollbar thumb can change length while scrolling far into unmeasured items. Staggered grids deal each item to the shortest lane when first composed and keep it there; they hold the item at the start of the first lane in view still while items above it in that lane are measured (other lanes can shift). `animate_item` slides the items that stay, for a short while after the keys change, in lists and staggered grids; items that appear are not faded in and removed items vanish at once. A sticky header is drawn a second time over the list, so it needs an opaque background; `lazy_sticky_list` pins at the top and `lazy_horizontal_sticky_list` at the left edge, and neither mirrors in a right-to-left layout.
- There is no `Modifier::animate_item`. A single item cannot animate its own placement through a callback in `rustle-ui`: the position a parent gives a child is only known during paint, and paint, hit testing, scroll regions and the semantics tree are separate traversals that would all have to agree on the displaced position, while the callback would have to advance an animation clock (`rustle-animation` sits above `rustle-ui`) in the middle of a frame. Lazy lists and grids know their items' places when they compose, so `LazyContent::animate_item` does it there.
- Built-in controls describe themselves to assistive technology with more than a role: scroll areas (`vertical_scroll`, `horizontal_scroll`, so every lazy list too) accept scroll up, down, left and right requests and move by most of a viewport; text fields report their selection and accept set-text and set-selection (set-text not on read-only fields); sliders, switches and checkboxes accept a set value (`40%`, `on`, `false`); `title` and `top_app_bar` are headings; `snackbar` is a polite live region.
- A window with a `parent` is made a child of it in the system only where that does not confine it to the parent: an owned window on Windows, an attached window on macOS. X11 only offers parents that clip the child, and Wayland has none through winit, so there the parent only chooses what a modal window blocks.
- Scrollbars are drawn over the content at the end of the scrolling axis, and the strip along that edge takes the pointer from what is under it while the bar can be seen. Horizontal scrolling areas get one too; there is no way to move the bar to the other side.
- Text areas wrap at their width (`basic_text_area_no_wrap` scrolls sideways instead). Line height is one value per node, grown only by a span with a larger size, and a field's caret and selection use the layout of its text at the width it was laid out at. Underline, strikethrough and span backgrounds are rectangles from the shaped layout, not glyph decoration. Glyph advances are not snapped to whole pixels, so text sits at subpixel positions. `TextLayout` offsets are UTF-8 bytes while `TextFieldValue` counts characters. Bidirectional text follows the Unicode algorithm through cosmic-text, and a caret at the join of two runs sits at the logical position, not at both visual edges. A `selection_container` numbers blocks in composition order, so a selection moves if blocks are inserted before it, and it only knows blocks composed in the current pass (a lazy list drops those scrolled away). `layout_text`, `font_families` and `register_font` need a renderer to exist; fonts registered earlier are queued and added when it is created, and they reach every renderer on the thread, because the renderers share one font system.
- Rounded clips (`clip_rounded`) each cost a texture the size of the window and an extra pass, so many of them on one screen (a message bubble per row, say) are slower than a rectangular `clip`; pointer input is still cut to the rectangle. `Modifier::alpha` fades each thing on its own; use `graphics_layer` for group-correct fading, rotation and scale, which draws the content to a texture the size of the window. Pointer input in a rotated or scaled area still goes where the area was laid out. Raised layers (`z_index`) are cut to the clips around where they were declared; use `z_index_unclipped` for popups, menus and dialogs that must leave a clipped or scrolling parent (`floating` and `dialog` do).
- Input is the mouse buttons (primary with double and triple click counts, plus secondary, middle, back, forward and others through `on_pointer_button`), a touch contact treated as the primary button, long presses, hover, the wheel, the keyboard (logical and physical keys, repeats and releases) and input-method text. Drag-and-drop, long presses and click counts are primary-button only, and a secondary or middle press does not move focus. Key bubbling follows layout containment, not the focus tree, so an `on_key_event` must be outside the `focusable` it wants to hear from. Only the primary button's presses carry a click count beyond one. Input-method composition is shown only in text fields: the caret rectangle is the caret's line, preedit styling (several segments, highlighted clause) is a single underline, and the platform's `ime_purpose` and surrounding-text API are not used. There are no key-chord sequences, global (outside the window) shortcuts, gamepads or pen pressure. Pinch gestures, files dropped from other applications, and dragging content from a `drag_source` (or, with `drag_source_button`, from a secondary-button drag) to a `drop_target` inside the application are supported. Several fingers are tracked at once (`Modifier::pointer_input`, `transformable`), and `ScrollState` and `ScrollableState` fling after a drag; the mouse takes part in the raw stream through its primary button only, and the wheel reaches `pointer_input` areas before `scroll` areas. Pressure comes from the touch force winit reports (0.5 when it reports none); winit 0.30 cannot tell a pen from a finger, so a pen is `PointerKind::Touch` in a window and `PointerKind::Pen` only when an `Embedded` host says so with `Embedded::contact`. Nested scrolling is explicit: a child is given its parent's `NestedScrollConnection`, not found through the tree. Nothing can be dragged out of the window.
- Accessibility describes a flat list of areas with their role, label, value and state, and supports click and focus requests.
- Right-to-left layout is supported by providing `LOCAL_LAYOUT_DIRECTION`: rows, stacks, flows and start-aligned columns mirror, text starts on its own side, and `padding_directional` swaps. Scroll directions, sliders and other widgets do not mirror, and text is not localized.
